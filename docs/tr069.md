# TR-069 on the Excitel ONU — what the ACS can reach

UBIQCOM UB5021 GVW-D, `V2.1.08-260703-UBLL`. Everything else is documented in
`notes/lockout.md` and `cli.md`. This one is about the line's provisioning channel,
because it is the last writable door left. Root, telnet and ftp are all shut, the ACS is
the one thing that is proven to write config to this box.

It is open now. A 350-line stdlib ACS (`tools/acs.py`) reads the whole parameter tree,
and the tree handed over the uid-0 telnet password. How the ONU was made to reach it is
the interesting part, because every obvious route is blocked by the firmware.

## What the device reports

`show tr069` (on the ONU's CLI, reachable as `excitel` over ssh) prints the ACS url,
the ACS username and password, the connection request url path, its auth pair and the
port, and the inform interval. The actual values are in `captures/onu-cli-show.log`,
which is gitignored, so keep them there and don't retype them into tracked files.

Two directions matter and they are not the same credential:

| value | direction |
|---|---|
| ACS url + ACS user/pass | CPE → server, the ONU authenticating itself on `Inform` |
| connection request user/pass + port | server → CPE, "call me now" instead of waiting the interval |

The inform interval is 300s, so any test where the ONU has to knock first costs up to
five minutes per attempt.

## Reference firmware, Syrotech SYRO-2010 (different ODM, same RTL9607C lineage)

Extracted the squashfs images from `firmware/` with `PySquashfsImage` (no unsquashfs on
this mac, it goes through `uv run --with`). Not our box, so treat all of this as what the
codebase can do, not as what ours is set to. Reproduce with:

```bash
uv run --with PySquashfsImage python tools/unsquashfs.py \
    firmware/SYRO-2010_all_V2.1.08-260731_GoipBsnlver/rootfs  /tmp/syro-rootfs
uv run --with PySquashfsImage python tools/unsquashfs.py \
    firmware/SYRO-2010_all_V2.1.08-260731_GoipBsnlver/custconf /tmp/syro-custconf
```

`usr/bin/cwmpClient` contains the vendor object and the write path:

```
X_CT-COM_TeleComAccount          vendor super-admin object
WebSuperAdminEnable              enable/disable web super admin
ERROR: Get superuser name from MIB database failed.
ERROR: Set superuser password to MIB database failed.
```

Those two errors are shared with `boa` and `cli`, which tells you all three front ends
write the same MIB keys `SUSER_NAME` / `SUSER_PASSWORD`.

Not filtered either. `etc/setprmt_reject` exists as the SetParameterValues denylist and
**every line in it is commented out**, so nothing is refused by default in that build.

Factory defaults sit in `custconf/config_default.xml`:

```xml
<Value Name="SUSER_NAME"      Value="admin"/>
<Value Name="SUSER_PASSWORD"  Value="PWI5efSKPj2skh/VAEbEbjk1Mjc5NTI3"/>
<Value Name="TELNET_USER"     Value="admin"/>
<Value Name="TELNET_PASSWD"   Value="PWI5efSKPj2skh/VAEbEbjk1Mjc5NTI3"/>
<Value Name="CWMP_CONFIGURABLE" Value="7"/>
<Value Name="CF_PASS_DECRY_ENABLE" Value="1"/>
```

Three things fall out of that.

Telnet has its own MIB keys and they default to the same value as the super user
password. There is no `/etc/passwd`, no `/etc/shadow` and no `/etc/ftpusers` anywhere in
the reference rootfs, and telnetd is started bare from `etc/inetd.conf`:

```
telnet stream tcp nowait root /bin/telnetd
ssh    stream tcp nowait root /bin/dropbear -i
```

So telnet auth on this lineage is MIB based, not shadow based. Confirmed on our box from
the other direction: the CWMP `ServiceManage.TelnetUserName` / `TelnetPassword` pair is
readable in clear and is a working root login, and it is a different password from the web
super user's. `excitel` failing with a visible `Error!` and `root` closing silently were
two different stores answering, not a wrong password.

Passwords are stored reversibly, not hashed. `PWI` prefix, `CF_PASS_DECRY_ENABLE=1`, and
the strings `xponlock_xor_encrypt` and `20src*xml*xor25` in the binaries. A config dump
would hand over plaintext credentials, which is why the blocked export in
`export-attempts.md` matters more than it first looked.

Also `CWMP_CONFIGURABLE=7` is read by `boa`, `configd` and `led`. It gates what CWMP is
allowed to reconfigure and its meaning is not decoded yet.

## The ACS

`tools/acs.py`, stdlib only, no `--set` at all:

1. `Inform` → `InformResponse`, every request and response logged verbatim
2. `GetParameterNames` `NextLevel=1` over `InternetGatewayDevice.` (falls back to
   `Device.` on fault 9003/9005), depth-limited recursion
3. `GetParameterValues` in batches of 16, first for names matching
   `pass|pwd|secret|user|account|admin`, then `--all-values` for everything
4. `--upload-url` adds `Upload` FileType 3 and accepts the CPE's `PUT`
5. session ends with 204

Output: `captures/acs-<stamp>.log` (raw XML) and `captures/acs-state.json` (queue,
writable flags, values), both gitignored. A dropped session resumes from the state file
on the next `Inform`; `--reset` starts over. Secrets print masked on the console.

```bash
python3 tools/acs.py --bind 0.0.0.0 --port 7547 [--all-values] [--upload-url URL]
```

## Getting the ONU to reach it

This cost the whole evening. Three separate firmware behaviours, each of which produces
the same symptom: complete silence, nothing in the listener's log.

**The CWMP socket's source address is pinned to `ppp0`.** Point the ACS url at
`192.168.1.33:7547` and `tcpdump` on the JIDU's wan shows the SYN arriving with source
`<ONU-WAN-IP>` — the ONU's own CGNAT WAN address — while the destination is on its LAN.
The reply is addressed back to that CGNAT address and the CPE drops it (bound device), so
the handshake never completes. DNAT, ip addr aliases, an `ip route` back-hack and a
userland proxy all fail for the same reason. A LAN ACS is impossible on this build.

**No SNI.** `cwmpClient` links OpenSSL and verifies certs, but there is no
`SSL_set_tlsext_host_name` call site anywhere in the binary. Tailscale funnel, cloudflared
and ngrok all route TLS by SNI, so every TLS-terminating proxy fails, at the proxy, with
nothing arriving here.

**Hostnames get an AAAA.** `gLibUseIpv6[1]` at startup, one address family picked per
connect (`soap->ipver`, `selected ai_family`), and the box has no global IPv6 — only
`fe80::`. So `https://<name>/acs` resolves, picks `2a00:dd80:…`, and dies before TCP.
With a literal IPv4 it dials fine, which is the tell.

What works is therefore the least clever option: **plain `http://` to a public IPv4**.
A VPS with `ssh -R 0.0.0.0:8080:127.0.0.1:7547` (needs `GatewayPorts yes`) puts the
listener on the internet, and the url is `http://<vps-ip>:8080/acs` — no DNS, no TLS, no
SNI. Before crossing the internet, set the CPE's ACS username/password to dummies with
`config tr069 acs username "acs" password "acs"`; our ACS ignores auth, and the real
pair stays in `captures/onu-cli-show.log` for the revert.

## What the tree gives

One session, 644 requests: 3760 parameters, 606 objects, 268 values read by name match.
The two objects the whole exercise was about:

| parameter | value |
|---|---|
| `DeviceInfo.X_CT-COM_TeleComAccount.Username` / `.Password` | `excitel` / **masked** (`********`) |
| `DeviceInfo.X_CT-COM_ServiceManage.TelnetUserName` / `.TelnetPassword` | `root` / real, uid-0 login |
| `DeviceInfo.X_CT-COM_ServiceManage.FtpUserName` / `.FtpPassword` | `e8ftp` / same string, real |
| `DeviceInfo.X_CT-COM_ServiceManage.TelnetEnable` / `.TelnetPort` | writable |
| `DeviceInfo.WebSuperAdminEnable` | `1` |
| `X_HW_Security.AclServices.TELNET{Wan,Lan}Enable`, `TELNETWanPort`, `TELNETWanSpecificIp` | writable |
| `ManagementServer.STUNUsername` / `.STUNPassword` | `excitel` / real |
| `WLANConfiguration.N.KeyPassphrase` | masked (`******`, `CWMP_SHOW_WIFI_PASSWORD=0`) |
| `ManagementServer.Password`, `WANPPPConnection.1.Password`, `UserInfo.Password` | empty |

The mask is the point to notice: `TeleComAccount.Password` and the Wi-Fi keys come back as
asterisks of matching length, so a length-based guess looks like a real secret. Only the
service accounts (telnet, ftp, STUN) are returned in clear.

So `X_CT-COM_TeleComAccount` is present, writable, and maps to the **web super user**
(`SUSER_*`), not to root. The CWMP `ServiceManage.Telnet*` object is what carries the
telnet/`/var/passwd` account, and reading it is how the uid-0 password came out — no write
needed. `ManagementServer.*` and the PPPoE password are masked by the daemon even though
the CLI prints the ACS pair in clear.

Root over telnet is the same restricted tree as `excitel`: same five commands, empty
`debug`, `config account` still only `password`. The label buys nothing but the password
itself was a result. Expect `CLI busy !!` if an ssh session holds the lock.

## Upload: the config file is encrypted

`Upload` FileType 3 is accepted and the CPE PUTs 178,676 bytes. It is not XML and not
compressed: 7.92 bits/byte, all 256 byte values, no periodicity at any period up to 256,
and 27% repeated 16-byte blocks. So a block cipher, not the `20src*xml*xor25` obfuscation
the strings suggest. The key is inside the vendor's `xmlconfig` and not recovered; until
that changes, the parameter tree is the readable config and the file is a dead end.

## CLI quirks that cost hours

- Writes land in the MIB and `show tr069` reflects them immediately, but the running
  daemon only re-reads on `config tr069 disable` / `enable`. A write with no bounce does
  nothing observable.
- The connection-request listener dies silently after repeated bounces. Same fix: bounce.
- `config dns` (`auto`, or three servers) does **not** change what the resolver answers.
  `/var/dnsmasq.conf` is generated with ISP resolvers bound to the PPPoE source address
  (`server=<ACS-IP>@<ONU-WAN-IP>`), and it pins `pulse.excitel.in` and `gz.gdqoe.ct`
  to them explicitly, so neither `config dns` nor a DNS hijack of the ACS name can move it.
  What `config dns` does change is what DHCP advertises to clients.
- `config dnspool ip "a" "b"` does affect the DHCP/DNS path — and after setting it the ONU
  stopped answering DHCP (`udhcpc: no lease` on the JIDU), which took the whole LAN's DNS
  down. `udhcpd -S /var/udhcpd/udhcpd.conf` and `dnsmasq -C /var/dnsmasq.conf` were both
  still running, so it was config state, not a dead daemon. `dnspool` is not cosmetic.
- `config save` persists runtime changes. That is what makes an ACS url change dangerous:
  saving a wrong url leaves the CPE off its ISP's provisioning across reboots.

## CLI write path, confirmed

Probed the command and wrote the current values back. Everything took, and `show tr069`
still reports the same url, user, pass, interval, path and port afterwards.

```
config tr069 acs     [ url "s" ][ username "s" ][ password "s" ][ inform "enable|disable" ][ interval "n" ]
config tr069 request [ username "s" ][ password "s" ][ path "s" ][ port "n" ]
config tr069 disable
config tr069 enable
```

Ordering is the only trap. You can pass any subset, but the keywords have to appear in the
order above. `acs interval "300" inform "enable"` is rejected with
`can not recognise arguments` because `interval` comes after `inform` in the grammar;
`acs inform "enable" interval "300"` is accepted. `acs url "..."` alone and
`acs url "..." inform "enable"` both work, so the middle keywords can be skipped, they
just cannot be reordered.

A successful write echoes every `arg_name` / `arg_value` pair back with no confirmation
line, and a bad one prints the usage block instead. That echo is why the realistic test
has to either redact the output or avoid the fields that carry secrets, `password` gets
printed in clear by the CLI itself.

So the MIB is writable from the CLI and a `SetParameterValues` equivalent is not needed to
change the ACS url. `config account` only ever accepts `password` and its table does not
include `root`, under either login name.

## FTP: root, unchrooted, and the plaintext config

The `e8ftp` pair from the tree is the whole game — user and password are the same string,
and it is the value stored in `captures/ftp-lastgood.xml`, not retyped here. `etc/inetd.conf`
starts the daemon as root:

```
ftp    stream tcp nowait root /bin/ftpd
```

and it is not chrooted — the login lands in `/var/tmp` and `/`, `/etc`, `/var/config` are
all readable. From the laptop:

```bash
curl -s --list-only "ftp://$FTP_USER:$FTP_PASSWD@192.168.1.1//var/config/"
curl -s "ftp://$FTP_USER:$FTP_PASSWD@192.168.1.1//var/config/lastgood.xml" -o captures/ftp-lastgood.xml
```

`/var/config/lastgood.xml` is 178 KB of **plaintext** MIB: `CF_PASS_DECRY_ENABLE=0` and not
a single `PWI` value in the file, so the encoding question is moot for this build. What is
in it, by key rather than by value (the file is gitignored):

- `SUSER_NAME`, `SUSER_PASSWORD`, `TELNET_USER`, `TELNET_PASSWD`, `FTP_USER`, `FTP_PASSWD`
  — all set, and `SUSER_PASSWORD` and `TELNET_PASSWD` are the same string
- `pppUser`, `pppPasswd`, `pppServiceName=excitel`, `pppAuth=0`, `ChannelMode=2`, `NAPT=1`
  — the service name is `excitel`, not `excitel_sys` as `export-attempts.md`
  guessed
- `CWMP_ACS_URL`, `CWMP_ACS_USERNAME`, `CWMP_ACS_PASSWORD` in clear
- `WLAN1_SSID`, `WLAN1_WPA_PSK` in clear
- `CWMP_CONFIGURABLE=6` (the reference build ships 7)

`/etc/passwd` is a symlink to `/var/passwd`, which `configd` regenerates from the MIB:

```
excitel:<md5>:0:0::/tmp:/bin/cli
user:<md5>:1:0::/tmp:/bin/cli
nobody:x:0:0::/tmp:/dev/null
```

So `excitel` is already **uid 0** — the restricted tree is a shell, not a privilege level.
`/bin/cli` is what the firmware puts in the shell field; `prmt_apply` is what writes that
file from the MIB. Which is the whole story of this box: root privileges, no shell.

The same file explains two earlier results: `custname` is `UbicomexcitelXPSETver`, which
matches `excitel` but none of the `optiLinkexcitel` / `Goipexcitel` / `Dbcexcitel` /
`Technxtexcitel` strings `boa` checks, so `formSaveConfig` was never going to answer.

Also worth knowing, and not Excitel's: the MIB carries a second management channel,
`CWMP_MGT_URL=189cube.com`, `CWMP_MGT_PORT=12112`, `CWMP_MGT_LOCATEPORT=17998`,
`CWMP_MGT_HEARTBEAT=60`. The CPE phones a third-party cloud independently of the ACS.

`/bin/ftpd` runs as root, so `STOR` writes anywhere on a read-write filesystem. Done once,
as the last step of this investigation: `/var/passwd` was rewritten with `/bin/sh` instead
of `/bin/cli` on the `excitel` line, and `ssh excitel@fe80::…%wan` then drops a uid-0 shell
(`#`) instead of the CLI. The file is tmpfs and `configd` regenerates it from the MIB, so a
reboot or any account write takes the shell away again. `captures/ftp-passwd.orig` is the
original line set.

The shell is busybox without `id`, `uname`, `whoami` or `head`, so `id` fails for reasons
that have nothing to do with privilege; `cat /proc/self/status | grep -i uid` is the honest
check. Also present in `/bin`: `mtd_util`, `flash_erase`, `xmlconfig` — the commands that
can brick the box — next to the useful ones: `tcpdump`, `iptables`, `spppctl`, `brctl`,
`mib`, `nv`, `vsEncrypt`.

This is the shortest route to the box and it made the ACS detour unnecessary in hindsight.
It stays because the ACS is what produced the telnet and FTP credentials, and because a
future firmware may close FTP while leaving the ACS open.

## Revert runbook

Do this in order. The saved config carries the test url, dummy ACS credentials and the
dnspool change, so a reboot without it leaves the CPE off Excitel's provisioning.

```
# ONU, over ssh + CLI
config tr069 acs username "excitel" password "<real, from captures/onu-cli-show.log>"
config tr069 acs url "http://pulse.excitel.in:7547/acs" inform "enable" interval "300"
config dns auto
config dnspool clear
show tr069
config save
reboot
```

Then, once the JIDU has its DHCP lease back:

```bash
# JIDU
udhcpc -i wan && nslookup example.com 127.0.0.1
uci del_list dhcp.@dnsmasq[0].address='/<name>/<ip>'   # funnel leftovers, if added
uci del_list dhcp.@dnsmasq[0].server='1.1.1.1'
uci set dhcp.@dnsmasq[0].noresolv='0'
uci commit dhcp && /etc/init.d/dnsmasq restart
ip addr del 192.168.1.34/24 dev wan                 # if the alias is still there
ip route del <ONU-WAN-IP>/32                      # if the route was added
uci show firewall | grep -i acs                    # drop acs-in / acs-fwd
```

And on the VPS / laptop: `ufw delete allow 8080/tcp`, kill the `ssh -R`, kill socat and
`tailscale funnel --bg off` if it was used.

## Don't

Hit `pulse.excitel.in` with the ACS credentials from the laptop. Those are per-device
credentials for our own CPE and using them against the ISP's server is a different thing
to publishing an `Inform` to a box we own. Same line `notes/lockout.md` already drew for the CVE
routes.

Don't leave the CPE pointing at a test ACS after `config save`, and don't put the real ACS
credentials on a url that crosses the internet — the `Inform` carries them as plain
cleartext `Authorization: Basic`.

A config `Download` (FileType 3) is the other ACS primitive and it is a full MIB write,
not one field. It can brick or re-lock the device, so it comes after
`SetParameterValues` has been shown not to work, not before.
